## 1. Objective
Prove the 18 end-to-end scenarios of brief §47 **headless**, each as soon as its packages merge, and keep **replay, save/load continuation, conservation and switch neutrality exact** across every merge. Q3 runs each package's claims independently and reports discrepancies to the lead; **it does not fix package code** (brief §47: "do not claim a scenario has been demonstrated merely because supporting classes exist").

## 2. User-facing outcome
A checked, honest status per scenario (demonstrated headless / demonstrated in Unity / partly / not demonstrated, with the reason) in the D5 section of ACCEPTANCE_TESTS and the release checklist, and scenario files the lead can use for checkpoint demos.

## 5. Allowed scope
1. **`IntegrationFixtures`** (`DotNet/God.Runner.Tests/Integration/IntegrationFixtures.cs`, mirrored for EditMode under `Assets/God/Tests/EditMode/Integration/`): short-horizon worlds that do not wait for demographic viability (blocker 10): an established, fed band of 10–20 adults and children; a pair with an asset; two households with alternating shortfalls; a wounded NPC near a healer; a teacher and learner; a government council; an archived dead person for resurrection. Built only through scenario setup and scheduled commands (GAMEPLAY §9 rule 1).
2. **Scenario files** `DotNet/God.Runner/Scenarios/civdiv_s01.scenario.json … civdiv_s18.scenario.json`, each added **when its packages merge** (map below), with a headless check in `DotNet/God.Runner.Tests/Integration/Scenario<NN>Tests.cs` that asserts the behaviour from events and state (not from class existence). Package-provided scenario files (`civ_*`, `org_*`) are inputs; Q3's `civdiv_*` files are the acceptance versions.
3. **Replay**: `Replay_DivineScenario_Exact` (scenario 18: ordinary NPC actions, a suggestion, a command, a compulsion, a possession with movement inputs, an avatar walk and give, a heal, a smite, a resource creation, a commandment, a resurrection — grown merge by merge, each element added when its package lands); `Replay_SwitchGod`; `verify FILE` exit 0 and `replay FILE --record full` equal to the live Full recording (W-D5-2).
4. **P6 `Switch_Matrix`** after every merge: each package's suite with the other switches at 0 equals its branch tip; pairwise; all on.
5. **Conservation at day boundaries** in every integration run: goods C1 (with the miracle ledger: C7), C8 (every holder change has an actor within reach), population P-C (`living = founders + births + immigrants + resurrections − deaths − emigrants`), Mythic M1 (`MythicTrace`), control CT1 (spells pair), claims ORG-I2 (when C2 merged); also after save and load.
6. **Save/load**: re-run each package's `*_SaveLoadParity` on the merged head and an integrated save with every open state at once (an open compulsion, a possession, a manifested avatar, an open service request, an open loan, an archived mind) → continue = straight run; second save byte-identical (H-D5-5).
7. **`Unity_Agrees_With_Runner`** on the divine replay (`Assets/God/Tests/PlayMode/UnityAgrees*.cs`): the same replay in Unity batch PlayMode and in the runner give equal checkpoint hashes (H-GS-3 pattern). Run at checkpoint Unity runs only (lead's slots).
8. **The D5 section of `docs/stage4/ACCEPTANCE_TESTS.md`** (Q3 owns it): the 18-scenario status table, the D5 test ids used by the package specs (ORG-*, SVC-*, W-D5-*, K-D5-*, H-D5-*, P1–P9, package ids), each with result, date, commit and who ran it; never weakening an existing criterion.
9. **Discrepancy reports** to the lead: when a package's claim does not reproduce, a short report with the command, seed, tick, expected vs observed — no code fix in the package's files.

## 16. Performance considerations
The integration suite must stay fast enough to run after every merge: short horizons (2–10 days), ≤ 20 seeds only where a scenario's criterion is statistical, `--workers 4`, and nothing during benchmark slots. Mark long checks `[Category("Integration-Long")]` and run them at checkpoints only.
